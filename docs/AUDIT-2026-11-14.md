# aino 全项目深度审查（2026-11-14）

审查对象：`1a8c39e` 之后的工作区（`aino.hpp` 14,161 行，版本 0.5.0）。  
本文是**分析记录**，不含代码改动，也未提交。第 3~6 节的问题编号（C/H/M/L）用于后续分批修复引用。

与既有文档的关系：`docs/13-project-review.md`（下称「13」）与 `docs/14-platform-status.md`（下称「14」）  
已经记录了 18 个批次的修复与平台能力矩阵。本文不重复它们已完成的结论，只做三件事：

1. 复核它们标记为"已完成"的项是否真的闭合（发现 2 处未闭合、3 处文档已过期）；
2. 补充 13/14 没覆盖的项（实测性能数字、死代码、跨平台反例、工程化缺口）；
3. 给出可执行的排序。

**所有性能数字都是本机实测**（MinGW GCC 16.2，`-O2`，无窗口离屏），复现命令见附录 A。

## 0. 结论摘要

| 维度   | 结论                                                                                                                        |
| ---- | ------------------------------------------------------------------------------------------------------------------------- |
| 架构   | 分层干净、无循环依赖、平台隔离彻底。单头文件是真实约束而非包装，取舍有迹可循                                                                                    |
| 代码质量 | 注释密度与质量远超同类项目；`-Wall` 零告警；命名与风格整体一致                                                                                       |
| 性能   | 组件级有两处真瓶颈：**大模糊投影 3.9 ms/帧**、**textarea 随行数线性退化到 9.8 ms/帧**                                                               |
| 稳定性  | 核心路径（状态表、浮层闸门、生命周期）设计严谨；**X11 剪贴板会破坏桌面剪贴板**是唯一的"伤害外部"缺陷                                                                   |
| 完整性  | Windows 后端基本完整；**macOS 后端只到"能开窗能画"**，键盘/剪贴板/关闭事件三块缺失，README 的"支持 macOS"需加限定                                               |
| 工程质量 | 测试资产极强（34 项 CTest、1600+ 像素断言），但**没有库目标**、探针目录一半是临时脚本                                                                      |
| 冗余   | 死公共 API 6 组（`icons::`、`begin_group/end_group`、`push_padding/pop_padding`、`row/column`、`scroll_visible`、`rrect_span`），零调用点 |

一句话：**这个库的"内核"（光栅化、立即模式状态机、浮层闸门、平台隔离）是工程级的；  
"外壳"（公共 API 面、macOS 后端、构建接入、测试资产治理）还停在个人项目水平。**  
下一步的收益主要在外壳，而不是继续打磨内核。

## 1. 项目整体架构

### 1.1 物理结构

```
aino.hpp 14,161 行
├─ 1–1360      公开 API（Color/Theme/Style/Input/Stack/Ui/Window/icons）
├─ 1362–14161  实现（#ifdef AINO_IMPLEMENTATION 单次展开）
│   ├─ 1453–2755   8.1–8.2  工具 + Canvas + CPU 光栅化（1300 行）
│   ├─ 2756–3193   8.3      文字抽象 + GDI 实现（437 行）
│   ├─ 3195–3360   8.4      主题工厂
│   ├─ 3360–3960   8.5      Ui::Impl（跨帧状态、缓存、闸门）
│   ├─ 4293–5060   8.6      图元
│   ├─ 5060–5216   8.7      Stack 布局
│   ├─ 5216–10003  8.8–8.16 组件（约 4800 行，最大的一块）
│   ├─ 10003–10301 8.17     滚动
│   ├─ 10302–10603          Window::Impl
│   ├─ 10604–11706 Windows 后端（1103 行）
│   ├─ 11709–13197 X11 后端（1489 行）
│   ├─ 13200–13675 macOS 后端（476 行）★ 只有另两个后端的 1/3
│   └─ 13676–14161 系统图标 / 图标缓存 / 平台图标加载
```

### 1.2 依赖方向（无环）

```
组件 (Ui::xxx)
  → detail::interact / animate_value / make_skin / paint_*        （无状态辅助）
  → Ui::Impl（状态表、缓存、闸门、裁剪栈）
  → Canvas（纯像素缓冲，无虚函数）  +  TextRenderer（唯一虚接口）
  → 平台后端（w32_* / x11_* / cocoa_*，仅在 #ifdef 内）
```

- 平台代码全部在实现区、且被 `#ifdef AINO_PLATFORM_*` 隔离，头文件部分零平台类型。
- `TextRenderer` 是唯一的运行期多态接口（5+4 个虚函数），`Canvas` 是 POD + 内联方法。  
  这个选择是对的：文字必须交给系统，几何必须自己画。
- 没有循环依赖，没有任何"上帝对象"持有平台句柄（平台句柄各在自己的 State 结构里）。

### 1.3 主要优势

1. **立即模式 + 显式状态拥有者**。`state_scope()` / `release_state_scope()` 把"隐藏要保留状态、  
   删除才释放"这件事做成了一等公民。这是同类库（Dear ImGui 的 ID 栈、microui 的无状态）  
   都没解决好的问题，13 的 A04 记录了这个演进过程。
2. **浮层输入闸门**（`Impl::gate_blocked` + `gate_claim`，3650–3711）。用"上一帧登记的矩形 + z 序"  
   解决立即模式的穿透问题，比"渲染顺序反着处理输入"更稳。注释里对 z 基准的两种取法  
   （入口 seq+1 vs `Z_FRAME_END`）说明这是踩过坑的。
3. **光栅化质量**。连续圆角（`corner_geo` 与 Figma squircle 逐项对齐）、4× 垂直子采样 +  
   水平解析覆盖、`RowPaint` 渐变快路径、`blend_row` 的 0..256 定点 alpha —— 这些不是"够用"级别，  
   是有明确数值依据的实现。
4. **空闲 0% CPU 的工程实现**。`WakeSignal`（内核事件 / 非阻塞管道）、  
   `hover_would_change` 过滤、`repaint_timeout_ms` 给光标闪烁排帧、`self_repaint` 区分  
   "组件自请求"与"输入驱动"—— 这套东西在 Windows 上是真验证过的。

### 1.4 架构问题

| 问题                 | 说明                                                                                                                |
| ------------------ | ----------------------------------------------------------------------------------------------------------------- |
| 单文件已到规模上限          | 14,161 行，`appearance` 类改动要在大文件里跳 1000 行。仍然可行，但已到需要"物理拆分 + 单文件分发由脚本拼装"的临界点（见 7.R7）                                 |
| 公共 API 面 > 实际维护能力  | 约 60 个组件方法 + 50 个图元 + 6 组遗留接口没有任何调用点（见 5）                                                                         |
| `impl` 是 public 成员 | `Ui::impl` / `Window::impl` 公开，示例直接 `win.impl->canvas`（gallery 1568）、探针直接改 `impl->focus`。等于把内部结构当 ABI，任何重构都是破坏性变更 |
| 后端能力不对称            | 1103 / 1489 / 476 行。macOS 不是"少几个测试"，是"少几块实现"                                                                      |
| 没有库目标              | CMake 里只有 `aino_add_demo`，没有 `add_library(aino INTERFACE)` / install / export。接入方只能拷头文件                           |

## 2. 各模块详细审查

### 2.1 基础类型与主题（1–440）

- `Color` 完整（`over()`/`luminance()` 的语义边界写得很清楚，`state_fill` 里那段"半透明底色不能 mix"的  
  注释解释了真实 bug）。`Rect` 的 `cut_*`/`intersect`/`center*` 覆盖到位。
- **M2（中）**：`Theme::same_as`（371–418）手写 ~60 项比较。加一个新 token 忘了同步 → `set_theme`  
  判定"没变" → 换主题不重绘，且**没有任何编译器提示**。这是典型的"沉默失败"设计。  
  建议：用 `#define AINO_THEME_FIELDS(X)` 生成成员声明、比较与工厂赋值三处；或给 `Theme` 加  
  `static_assert(sizeof...)` + 把颜色聚成 `Color colors[N]` 数组。
- **M14（中，文档）**：`Theme` 保留 18 个兼容字段（`background`/`card`/`primary`…），由 `light()/dark()`  
  映射。文件头说"保留兼容"，但没有 `AINO_DEPRECATED`、没有迁移说明，新用户会同时看到  
  `label` 与 `foreground` 两套语义而不知道用哪个。

### 2.2 Canvas 与光栅化（1636–2755）

质量评估：**本项目的核心竞争力所在**。

- 快路径覆盖到位：不透明整行 `uint32` 填充、半透明定点 `blend_row`、`rrect` 内区覆盖率恒 1 时整行快填、  
  描边竖边恒 1 区快填。`clear()` 用首行 + `memcpy`（注释给了 3 ms → 0.2 ms 的实测）。
- 空哨兵 `(xl=1, xr=0)` 的坑在 `raster_rrect_paint` 与 `raster_rrect_stroke` 两处都显式处理了，  
  并在注释里写明"直接用 min/max 会被带偏"。
- **M4（中）**：`shadow_cov`（2526–2543）用 `static float tab[65]; static bool init;` 手工懒初始化，  
  不是线程安全的；同一文件里 `ring_lut()` 用的是 magic static（线程安全）。两套风格并存。  
  单窗口单线程渲染下无碍，多窗口多线程（gallery 的素材窗口正是这种）就有数据竞争风险。  
  修法：改成 `struct { float tab[65]; ShadowLut(){...} }` + `static const ShadowLut& lut`。
- **优化点（见 4.2）**：`raster_shadow` 没有 "内区恒 1" 的快路径，也没有降采样 —— 与 `blur_backdrop`  
  的处理方式不一致（后者先 1/2 或 1/4 降采样再模糊）。大 blur 的投影因此成为整帧最大单项。

### 2.3 文字渲染（2756–3195）

- GDI 实现细节扎实：`strict_utf8_decode` 快路径 + 逐段 ANSI 兜底（混合编码）、  
  GDI 状态缓存（`cur_font_/cur_color_/cur_bk_`）、`ETO_CLIPPED` 省三次 DC 往返、  
  `ANTIALIASED_QUALITY` 而非 ClearType（有实测依据：彩边最大通道差 174）。
- `measure_cache_` 满了整体 `clear()`（3013）—— 简单但会造成周期性抖动（每 2048 条清一次，  
  清空后下一次测量全部回落到 GDI 往返）。同类问题 `adv_cache`（4766，8192 条）也一样。  
  建议换成 LRU 或"清一半"，成本极低。
- **L4（低）**：公开的 `Ui::line_height(font_size)` 没有 weight 参数，内部固定 400；  
  而 `draw_text` 内部用的是 `line_height(pfs, weight)`。粗体文本的"量高"和"画高"来自两个字号。  
  GDI 下 `tmHeight` 通常相同，所以现在看不出问题，但这是一个会在换字体/换平台时爆的隐患。
- **H3（高）**：见 2.9。

### 2.4 Ui::Impl 与状态管理（3360–3960）

- `WidgetStateTable` 的 key 是 `(scope, id)`，测量模式新建的节点在 `set_measuring(false)` 时回收 ——  
  这个设计避免了"测一遍就产生幽灵状态"。
- `release_scope` 会收缩高水位 bucket（`compact.merge`），注释解释了为什么不能靠 `rehash` 缩容。到位。
- 三套缓存都有预算：`wrap` 6 MB（LRU，O(1) 淘汰）、`adv` 8192 条、`undo` 200 步 / 4 MB。  
  13 的 P02 已经处理过，复核通过。
- **M3（中）**：动画/状态 ID 用算术派生：`id * 41u + 1u`（toggle 6609）、`id * 43u + 2u`（slider）、  
  `id * 31u + 7u`（input 拖选锚点）、`base_id * 47u + 3u`（tabs 滚动）、`ids[i] * 83u + 1u`（菜单项）。  
  这些值与"另一个控件的真实 id"共用同一个 64 位空间，理论上可以相等（`make_id` 是 FNV 哈希，  
  输出在 64 位空间均匀分布，撞上 `id*41+1` 的概率不为零但极低）。  
  更现实的风险不是碰撞，而是**审查困难**：想知道某个 `flags` 槽属于谁，得反算。  
  建议：给派生 ID 定义 `detail::sub_id(id, slot)`（高位标记 0xA1 前缀），语义显式且可断言。
- **L7（低）**：`begin_frame` 重置了 `group`、`pad`、`clips`、`clip_logic`，但没有清 `scroll_stack`。  
  正常路径由 `ScrollScope` 析构保证平衡；一旦帧回调抛异常（用户的 `std::stoi` 等），  
  下一帧就在"上一个滚动区里"开始画，症状是整页偏移一个滚动量 —— 很难查。  
  一行 `impl->scroll_stack.clear()` 成本为零。

### 2.5 图元（4293–5060）

- 每个入口都有 `measure_on` 分支，且测量与绘制用同一份 `Rect`。
- `inner_shadow` 刻意不参与测量（注释说明"内阴影不占布局"），合理。
- **M5/M8（中）**：`system_icon`（14120–14152）每帧对每个图标做 `size×size` 次 `Canvas::blend`，  
  每次 `blend` 都要重新判裁剪、算浮点 alpha。实测 16×16 = 1.02 µs、24×24 = 2.12 µs/个。  
  一页 60 个图标 ≈ 0.07–0.13 ms，不算瓶颈，但这是**纯重复计算**：  
  掩码是常量，颜色每帧相同，完全可以按 `(icon,size,color)` 缓存一张预乘 ARGB 位图后整行合成。

### 2.6 布局（5060–5216）

- `Stack` 是纯值语义（一个 Rect + 方向 + gap），`next/next_frac/next_text/fill/part/skip` 覆盖了实测需要的全部用法。
- 刻意不做内容自适应高度 —— 这个取舍有充分理由（见注释 640–642），且 `begin_measure()` 提供了替代路径。
- 但测量是**两趟绘制**，代价明确（840 行注释也写了）。对"卡片高度"这种高频需求，  
  两趟意味着每帧多一次全量布局计算。中长期值得做的 opt-in 单趟"两阶段排版"（见 9.M4）。

### 2.7 组件（5216–10003）

整体质量高，统一走 `make_skin` / `paint_surface` / `interact` / `animate_value` 四件套，  
外观一致性靠这三个函数保证，而不是靠每个组件自己抄颜色。

问题集中在**重复**与**逐帧分配**：

- **M7（中）**：`end_scroll`（10197–10213）与 `scroll_bar`（10273–10288）各写了一遍  
  "算 prev → 判 moved → 取 alpha → 画 → 需要时 repaint"，且两者的 `prev` 键**不一致**：  
  前者 `hash_combine(ctx.id, "scrollprev")`，后者 `scrollbar_id(impl, "scrollprev", box)`。  
  今天两者恰好等价（因为 `scrollbar_id` 在栈顶 box 相同时会退化成 `widget_id`），  
  但这是"靠巧合成立的等价"，改一处就会漂。
- **重复实现（中）**：文本编辑语义写了两份。`input` 的 Ctrl+Z/Y/C/X/V/A（6231–6378）  
  与 `textarea` 的同组（7372–7531）逻辑相同、边界不同（password 过滤、单行控制字符过滤、  
  换行处理）。`input_otp` 又是第三份。约 400 行近似代码。
- **M10（中）**：`table` 每帧 `std::vector<bool> num_col(cols)`，并对每个单元格调用两次  
  `looks_numeric`（表头判定一次、绘制时再一次，8013）。  
  1000 行 × 6 列 = 12000 次字符串扫描/帧。建议：把 `num_col` 与逐格对齐结果缓存在  
  `WidgetStateTable<...>` 里，按 `(table_id, rows.size(), 内容版本)` 失效。
- **L9（低）**：表头字号硬编码 11（7992），不读 `st.font_size`；用户放大字号时表头不跟随。
- **L6（低）**：`menu/select/combobox/context_menu` 打开时每帧 `std::vector<std::string> items_copy = items`  
  （8224、9371、9725、9888）。1000 项列表 = 1000 次 string 拷贝/帧。  
  这个拷贝是**有理由的**（deferred 回调在调用方栈帧结束后才执行，捕获引用会悬垂），  
  但可以改成"帧内先算好绘制指令/或要求调用方传 stable 引用"。

### 2.8 滚动（10003–10301）

- 设计正确："一个视口 + 一段内容高度"，虚拟列表是特例而非第二套 API。这点比大多数 GUI 库都干净。
- 嵌套滚轮的归属用"上一帧的滚动区快照 + 深度比较"解决，第一帧退化 —— 可接受，注释也写明了。
- **不一致（中）**：`scroll_visible()`（10243）是同一件事的低层版本，但**没有**嵌套让路  
  （`deeper_scroll_has_pointer`）、没有滚动条、键也用 `widget_id("scroll", box)` 之外的路径。  
  两套语义并存，用户按文档用低层 API 就会遇到"内层滚外层也滚"。
- `scroll_to_index`（10295）不做"已在视口内就不动"判断，每次都把目标顶到视口顶部 ——  
  键盘上下键导航时会跳。

### 2.9 文本编辑与测量模式（重点）

**H3（高）**：`draw_mono_text`（4711–4719）在 `measure_on` 时直接 `return`，**不调 `measure_add`**；  
而同族的 `draw_text`（4928）、`system_icon`（14124）、`fill_rect` 等都调了。  
后果：任何用等宽文字自绘的组件，在 `begin_measure/end_measure` 里量出来的高度都不含它。  
`AGENTS.md` 已经把这条写成了"使用它的示例必须自己计入宽高"，gallery 为此专门写了  
`mono_label()`（gallery 29–40）做手工补偿 —— 这是**用示例代码给库的缺陷打补丁**。

修法（不需要改 API）：入口改成

```cpp
if (impl->measure_on) {
    impl->measure_add(Rect(x, y_top, mono_width(text, fs, weight) * text.size() / ..., ...));
    return;
}
```

用 `mono_advance × 码点数` 与 `line_height` 就能算出精确外接矩形（等宽字体的优势正在于此），  
成本是 O(1)，然后删掉 `mono_label`。

### 2.10 平台后端

#### Windows（1103 行）—— 完成度最高

已复核的优点：DPR 感知、Per-Monitor V2、`WM_GETMINMAXINFO`、双缓冲 + `bb_valid` 防黑闪、  
`WM_PRINTCLIENT`（截图/缩略图）、IME 组合窗三件套（透明化 ghost 窗口 + 线程计时器 + 定位补偿）、  
`WinPreciseTimer` 高精度等待、剪贴板重试 + `GlobalSize` 兜底。

问题：

- **M1（中）**：`win_append_utf16`（10738–10751）用**函数级 static** `pending_high` 拼代理对。  
  这是进程级共享状态：A 窗口收到半个代理对、B 窗口收到下一个低代理 → 拼成一个错误的码点。  
  而且 `Win32State::high_surrogate`（10657）声明了却从未使用 —— 正确的家就在那里。
- **M10（中）**：`w32_destroy`（11358–11366）：
  ```cpp
  HBITMAP tmp = CreateCompatibleBitmap(s->mem_dc, 1, 1);
  if (tmp) { SelectObject(s->mem_dc, tmp); DeleteObject(tmp); }   // tmp 仍被选中 → 删除失败
  ```
  `DeleteObject` 对"仍被选进 DC 的位图"返回失败，这 1×1 位图每个窗口泄漏一个。  
  正确顺序：`SelectObject` 换出旧位图 → `DeleteObject(旧位图)` → 再 `DeleteObject(tmp)` 前先 `SelectObject(old)`。
- **M11（中）**：`Window::set_size`（11638）硬编码 `WS_OVERLAPPEDWINDOW` 算边框，  
  与创建路径里 `cfg.resizable` 的处理不一致（不可缩放窗口的尺寸会算错一个边框）；  
  且不会重算 DPI 变化后的 `min_pw/max_pw`。
- `win_create_backbuffer` 失败（`CreateDIBSection` 返回 null）时把 `has_backbuffer` 置 false，  
  之后 `render()` 永远早退、窗口黑屏且不重试。建议失败时保留旧缓冲并记录错误码。

#### X11（1489 行）—— 有真实伤害的缺陷

**C1（严重）**：`Window::set_clipboard`（13188–13194）

```cpp
Atom sel = XInternAtom(s->dpy, "CLIPBOARD", False);
XSetSelectionOwner(s->dpy, sel, s->win, CurrentTime);
(void)text;   // 只做形式上的所有权声明
```


`x11_handle`（13118+）没有 `SelectionRequest` / `SelectionClear` 分支。  
于是：用户在任何输入框里按一次 Ctrl+C → 本进程成为 CLIPBOARD 所有者 → 其它应用（浏览器、终端）  
再来粘贴时，会向本窗口发 `SelectionRequest`，**永远收不到 `SelectionNotify`** →  
对方超时（通常 2–5 秒）后拿到空内容。也就是说**这一下把整个桌面的剪贴板清空了**，  
不只是"aino 自己粘贴不了"。

这比"未实现"严重一档：13/14 记的是"剪贴板未完成"，实际行为是**破坏性**的。  
最小补救（10 分钟级）：在正式实现前，`set_clipboard` 直接 `return;`（不抢所有权），  
至少不伤害用户已有内容。完整实现需要 `TARGETS`/`UTF8_STRING`/`MULTIPLE` + INCR 大内容分块，  
14 已把它列为第 1 优先验收项。

其余：`x11_feed_input` 的键值/修饰键路径存在（未实机验证），XIM 焦点处理存在，  
`x11_present` 走 `XPutImage` 整块上屏（无 SHM，大窗口下比 SHM 慢，但对本项目定位可接受）。

#### macOS（476 行）—— 骨架

**C2（严重）**：键盘后端只做了"往 text_input 里塞字符"。

```cpp
inline void cocoa_key_down(id self, SEL, id ev) {
    CFStringRef chars = ... "characters" ...;   // 只取字符
    ...
    s->key_down[KEY_BACKSPACE] = false;         // 字面意义上把"按下"置 false
}
```

- 没有任何 `charactersIgnoringModifiers` → `KEY_LEFT/RIGHT/UP/DOWN/HOME/END/DELETE/ENTER/TAB` 映射；
- 没有 `modifierFlags` → `key_ctrl/key_shift/key_alt` 恒为 false（源码注释自己承认：  
  "目前 macOS 侧还没有代码往里写值 —— 能编译，但 ctrl_of() 恒为 false"）；
- 结果：macOS 上**输入框无法退格**（连 KEY_BACKSPACE 都不会触发）、无法回车提交、  
  无法方向键移动、Ctrl+C/V/Z 全部失效。

**C3（严重）**：没有关闭事件回写。`cocoa_create` 只注册了 `drawRect:`/`mouseMoved:`/`mouseDown:`/  
`mouseUp:`/`keyDown:`，没有 `windowShouldClose:`/`NSWindowDelegate`。点红叉后窗口消失但  
`Window::run` 的循环仍在（`running` 只由 `close()` 改），进程挂着。

**H2（高）**：空闲是 2 ms 轮询（`usleep(2000)`，13654），`WakeSignal` 的管道没有被  
AppKit 的 runloop 等待消费。500 次/秒唤醒 ≈ 空闲 1–3% CPU，直接违背"空闲 0% CPU"这条核心承诺。  
`docs/14` 已如实记录，但 README 首屏把 macOS 与 Windows 并列为"支持"，读者不会预期到这个差距。

其它：`cocoa_present` 每帧 `CGBitmapContextCreateImage`（整幅位图拷贝）+ `display` 同步绘制，  
比 Win32 的 `BitBlt` 贵一个量级；`scale` 固定 1.0（无 Retina）；`set_clipboard`/`clipboard` 是空函数。

## 4. 性能瓶颈与优化建议

### 4.1 实测基线（本机，MinGW GCC 16.2，`-O2`，1180×760 离屏缓冲）

| 项目                             | 参数                      | 实测                   |
| ------------------------------ | ----------------------- | -------------------- |
| 投影 `pop_shadow` level0（菜单）     | 240×200, blur 30, dy 5  | **0.91 ms/帧**        |
| 投影 level1（浮卡/toast/tooltip）    | 420×300, blur 44, dy 10 | **2.20 ms/帧**        |
| 投影 level2（dialog/sheet/drawer） | 480×300, blur 90, dy 30 | **3.92 ms/帧**        |
| 背景模糊 `blur_backdrop`           | 900×300, blur 16        | **2.12 ms/帧**        |
| 满窗半透明圆角填充（8% 底）                | 1180×760, r12           | **0.77 ms/帧**        |
| 图标合成                           | 16×16 / 24×24           | **1.02 / 2.12 µs 个** |
| textarea 100 行                 | 3.9 KB                  | 1.06 ms/帧            |
| textarea 1000 行                | 39.9 KB                 | 1.30 ms/帧            |
| textarea 5000 行                | 203.9 KB                | 2.52 ms/帧            |
| textarea 20000 行               | 828.9 KB                | **6.22 ms/帧**        |
| textarea 20000 行 + 全选          | 828.9 KB                | **9.78 ms/帧**        |

复现命令见附录 A。

### 4.2 优化 1：投影按掩膜缓存（预期最大的单项收益）

**原理**：投影的形状只由 `(w, h, radius, blur)` 决定，与位置、颜色无关。  
现在每帧对"外扩 1.35·blur 后的包围盒"逐像素求 SDF + 查表，于是成本 ∝ (w+2.7b)(h+2.7b) ——  
blur 从 22 涨到 90，面积涨约 4 倍，每像素还要一次 `sqrt`。

**方案（按收益/风险排序）**：

| 方案         | 做法                                                                             | 预期                                | 副作用                                 |
| ---------- | ------------------------------------------------------------------------------ | --------------------------------- | ----------------------------------- |
| A. 掩膜缓存    | `unordered_map<key, vector<uint8_t>>` 存 alpha 掩膜，合成时只有 `blend_row` 级的 alpha 混合 | 3.92 ms → **0.3–0.5 ms**（约 8–10×） | 内存：一个 723×543 掩膜 ≈ 392 KB；可只留最近 4 条 |
| B. 降采样重算   | 按 1/2 或 1/4 分辨率算 SDF 再双线性放大（`blur_backdrop` 已是这个套路）                            | 3.92 ms → **1.0–1.3 ms**（3–4×）    | 边缘略软，但 blur 本来就软，视觉无损               |
| C. 减小 blur | level2 从 90 降到 30（与文档记录的基准一致）                                                  | 3.92 ms → **0.9 ms**（4.3×）        | 视觉上"压不住整页"，需要产品决策                   |

推荐 A（B 作为缓存未命中时的降级路径）。**验收方式**：`tools/verify_render.py` 的  
"像素等价"思路——缓存路径与直接计算路径在同一帧输出上做逐像素 diff，要求 ≤1/255；  
再测 `AINO_FRAME_LOG=1` 下 dialog 打开时的"绘制 ms"。

### 4.3 优化 2：textarea 的每帧全量重建

**原理**：`split_lines(*value)` 每帧把整篇文本复制成 `vector<string>`（7295）；  
`utf8_count(*value)` 每帧分配一个 `vector<uint32_t>`（7324）；选区绘制对**所有**行  
（不只可见行）调 `utf8_count`，命中选区时还调 `line_x`（两次分配 + 一次 GDI 度量）。

**方案**：

1. 缓存"行起始字节偏移"数组，按 `(data 指针, size, 版本号)` 失效 —— 只在编辑时重算。  
   偏移数组本身就够画行、够把 caret 的码点换算成行列，不需要 `vector<string>`。
2. `utf8_count` 改成不分配的单遍扫描（当前实现是 `utf8_codepoints(s).size()`，1549）。  
   这一处改动同时惠及 `input`、`gallery` 的字数统计。
3. 选区/绘制循环改成"从可见区间起止"（`i0 = max(0, floor(tscroll/lh))`），与 `draw_text` 的做法一致。

**预期**：20k 行从 6.2 ms → **<1.5 ms**；全选从 9.8 ms → **<2 ms**。  
**验证**：`tools/probe/edit_probe.cpp` 扩一条"20k 行文档 200 帧平均时长"的断言（阈值可设 3 ms）。

### 4.4 优化 3：图标合成与裁剪

`system_icon` 当前每图标：`push_clip`（recompute 两次）→ `size²` 次 `blend` → `pop_clip`。  
`blend` 每次都要判 `clipped` 与四个边界。改成：

1. 普通 `fill_rect`/`stroke` 的裁剪已经在 canvas 层做，图标完全可以先把 4 条边算成  
   `[x0,x1) × [y0,y1)` 的矩形，再整行走定点混合（复用 `blend_row` 的定点 alpha 思路）；
2. 按 `(icon, size, argb)` 缓存预乘结果，命中时是一次 `memcpy` 式行合成。

**预期**：2.12 µs → 0.3 µs（24×24），一页 60 图标从 0.13 ms → 0.02 ms。  
**副作用**：多一层缓存内存（60 个图标 × 24² ≈ 34 KB，可忽略）。

| ------------------------------------- | ----------- | ---------------------- | ------------------ |
| `measure_cache_` / `adv_cache` 满了整体清空 | 3013 / 4766 | 清一半或 LRU               | 消除周期性抖动，无副作用       |

## 7. 推荐的重构方案

原则：**不动 API 语义、不动视觉、不做"为了重构而重构"**。每条都给出可独立审阅的边界。

**R1. 抽取 `detail::TextEdit`（收益最高，风险中等）**  
把 `input` / `textarea` / `input_otp` 共享的"码点 ↔ 字节、caret/选区、撤销栈、剪贴板、  
按键分发"收进一个内部结构体，三个组件只保留各自的几何与绘制。

- 影响面：`Ui::input/textarea/input_otp` 三个函数体，约 1200 行 → 约 700 行 + 一个 300 行的公共内核。
- 验证：`tools/probe/edit_probe.cpp` 已有 131 项编辑断言，改动前后必须全绿；再补一条"input 与  
  textarea 在同一组按键序列下产生相同文本"的对照断言。
- 风险：password 过滤与单行控制字符过滤的差异必须显式建模（现在是隐式的）。

**R2. 收敛滚动 API**  
`scroll()` 作为唯一入口；`begin_scroll/end_scroll` 保留为薄包装（已被 1 个示例使用）；  
`scroll_visible/scroll_bar/scroll_offset/scroll_to_index` 内部改调 `scroll()` 的实现。  
抽出 `scrollbar_draw()` 消掉 M7 的重复。

- 验证：`scrollbar_probe`、`interaction_probe`、`gallery_layout` 三组不回归。

**R3. 合成层分离（为性能与 SIMD 铺路）**  
新增 `detail::Compositor`：`icon_mask_blit()`、`shadow_cache()`、`span_blend()`。  
现有 `Canvas::blend` 保留为标量参考实现（同时充当 `raster_equiv` 的对照）。

- 收益：4.2/4.3/4.4 三条优化都落在这一层，互不干扰。

**R4. 平台契约探针**  
把 `docs/14` 的能力矩阵变成代码：`tools/probe/platform_contract_probe.cpp` 断言  
"若声明支持 X，则 `set_clipboard` 回调非空且往返成功"、"`Window::run` 在 N 帧后能响应 `close()`"。

- 价值：把"文档里写的缺口"变成"CI 会红的缺口"，避免继续漂。

**R5. 死 API 清理**（见 5.1）：`[[deprecated]]` → 0.6 删除；`icons::` 立即删。

**R6. 构建库化**

```cmake
add_library(aino INTERFACE)
target_include_directories(aino INTERFACE $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}>)
add_library(aino::aino ALIAS aino)
install(FILES aino.hpp DESTINATION include)
install(EXPORT ainoTargets NAMESPACE aino:: DESTINATION lib/cmake/aino)
```

示例改成 `target_link_libraries(aino_gallery PRIVATE aino::aino)`。  
纯增量、零行为变化，却让"能接入"从"拷文件"变成一行 CMake。

**R7. Theme 相等性自动化**  
`#define AINO_THEME_FIELDS(X) X(Color, tint) X(Color, label) ...` 生成声明、`same_as`、工厂赋值。  
代价是一次机械改造（约 200 行），收益是"以后加 token 不会静默漏比较"。

## 9. 项目发展建议与创新功能

定位复述：**单头文件、零依赖、CPU 光栅化、空闲 0% CPU、macOS 视觉**。  
判断标准只有一条：**它是否强化"极小体量的原生桌面工具"这个位置**。  
凡是需要 GPU、需要资源文件、需要第三方库的，都不该进核心。

### 短期（1–2 周，低成本高确定性）

**S1. 投影与图标的合成缓存**（已在本报告 4.2/4.4 量化）

- 理由：这是当前唯一"用户能直接感觉到"的性能问题（弹窗打开时掉帧）。
- 难度：低（纯内部改动，无 API 变化）。收益：3.9 ms → 0.5 ms。
- 优先级：P0。

**S2. 窗口控制 API（`minimize/maximize/hide/show/set_topmost`）**

- 理由：常驻小工具（剪贴板历史、下载器、监控面板）第一件事就是"最小化到后台"。  
  现在做不到，等于把"工具类应用"这个最大用户群挡在门外。三个后端都已具备实现条件  
  （`ShowWindow` / `XIconifyWindow` / `performMiniaturize:`）。
- 难度：低。收益：打开一个完整的应用品类。优先级：P1。

**S3. 托盘/状态栏图标（`aino::Tray`）**

- 理由：与"低占用常驻"定位天然契合；Windows `Shell_NotifyIcon`、macOS `NSStatusItem`、  
  X11 需要 `libappindicator`（可在缺失时降级为无托盘）。约 200–300 行/平台。
- 难度：中（X11 生态碎片）。收益：让 aino 成为"写小工具最快的方式"。
- 优先级：P1（Windows/macOS 先做，X11 标注降级）。

**S4. 文件拖放**

- 理由：拖一个文件到窗口是桌面应用的肌肉记忆；现在完全无响应，用户判定为 bug。
- 难度：中（三个平台的拖放协议）。收益：`image_well`、SSH 上传、任意"打开文件"场景直接受益。
- 优先级：P1。

### 中期（1–3 个月）

**M1. 单趟自适应高度（`Stack` 的 opt-in 两阶段）**

- 理由：`begin_measure` 的"画两遍"是当前最别扭的 API 体验，而"给卡片留多高"是最高频问题。  
  可以做 `auto_height(fn)`：先以 `w=none` 跑一遍收集高度，再真正画。本质仍是两趟，  
  但把"两趟"封装进库、并对纯文本/单行组件走单趟快路径。
- 难度：中高（要处理浮动元素与测量期副作用）。收益：示例代码量下降、新用户上手成本下降。

**M2. 键盘焦点与无障碍的最小闭环**

- 理由：Tab 序 + Enter/Space 激活 + `accessible_name` 元数据，是"能当正经工具用"的分水岭。  
  IMGUI 的长期短板正在这里，谁先补谁差异化。
- 难度：中（Windows UIA 桥接最难，可先做 Tab 序 + 自绘焦点环）。收益：企业/内网工具采购硬门槛。

**M3. 文本编辑抽取 + 软换行**（R1 + F6）

- 理由：`textarea` 是唯一"随内容规模退化"的组件，也是代码重复最重的地方。
- 难度：中。收益：性能 + 可维护性 + 长文本编辑体验，一次拿三样。

**M4. 静态库/CMake 包 + 一个 5 行 demo**（R6）

- 理由：接入摩擦是开源库的第一道流失点。"拷头文件"看着简单，实际挡住了  
  `add_subdirectory`/`find_package` 两种主流工作流。
- 难度：极低。收益：接入转化率。优先级：P0（性价比最高的一条）。

### 长期（季度以上）

**L1. 可选 GPU 后端（独立头文件，非默认）**

- 理由：CPU 光栅化在 4K/高 DPI 下的上屏与合成成本会线性上升；但这不该污染核心。
- 做法：`aino_gl.hpp` / `aino_d3d11.hpp` 实现同一 `Canvas` 契约（上传纹理 + 一次 blit），  
  核心库不变、依赖不变、体积不变（不 include 就不编译）。
- 难度：高。收益：大窗口/高分屏场景。风险：违背"零依赖"宣传，必须严格可选。
- 优先级：P3（先做 S1/M1，把 CPU 路径压到够用，再谈 GPU）。

**L2. WASM/Canvas 后端（在线 demo）**

- 理由：单头文件 + 零依赖的最佳展示方式就是"打开网页就能点"。一个 300 行的  
  emscripten 后端就能把 gallery 搬到浏览器，成为最好的 README。
- 难度：中（需要 emscripten 工具链与 CI job）。收益：项目可见度、issue 质量、贡献者入口。

**L3. 无障碍桥接（UIA / NSAccessibility / AT-SPI）**

- 理由：这是 IMGUI 架构的天然弱项，也是"能否进企业内网"的关键。  
  最小可用版本：每个交互组件登记 `(role, name, value, bounds)`，桥接层做查询与 Invoke。
- 难度：高（三个平台三套 API）。收益：差异化 + 合规。优先级：P3。

**L4. 组件级 golden 截图回归**

- 理由：现在的像素断言是"几何/颜色/裁剪"级别（`ci_pixels` 44 项），能证明"画对了形状"，  
  证明不了"看起来还是 macOS 味"。加一层"每页 × 深浅主题 × 96/144 DPI 的 golden PNG + 容差比较"，  
  才能在改视觉 token 时及时发现回归。
- 难度：低（已有 `verify_gallery.py` 与 `AINO_SHOT_BMP`）。收益：视觉一致性可回归。优先级：P2。

### 不建议做的

| 建议                          | 为什么不做                                                                   |
| --------------------------- | ----------------------------------------------------------------------- |
| 内建布局引擎（flex/grid/约束求解）      | 与"单头文件 + 可读完"直接冲突；`Stack` + 测量已覆盖 90% 场景                                |
| 内建控件树 / retained mode 双 API | 会分裂状态模型，立即模式的全部优势（无同步、无生命周期）都会被抵消                                       |
| 资源文件 / 主题 JSON              | 便携性卖点来源就是"一个 exe 一个头文件"，加资源即破功                                          |
| 内建图标字体                      | 现在走系统符号（Segoe Fluent / SF Symbols），跨平台字形差异已被文档承认；引入图标字体等于加 200KB + 授权问题 |

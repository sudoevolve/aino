## 1. 结论摘要

**谁最贵**（单帧绘制耗时，越靠前越贵）：

| 排名 | 组件            | 耗时          | 是 `label` 的 | 贵在哪                        |
| -- | ------------- | ----------- | ----------- | -------------------------- |
| 1  | `dialog`      | **2773 µs** | 17.7×       | 全窗遮罩 + `blur 22` 阴影 + 折行正文 |
| 2  | `sparkline`   | **868 µs**  | 5.5×        | 11 条带 AA 的线段 + 三角面填充       |
| 3  | `prim_shadow` | **616 µs**  | 3.9×        | 距离场阴影本身                    |
| 4  | `table`       | **603 µs**  | 3.9×        | 12 次文字绘制 + 斑马纹 + 网格线       |
| 5  | `toast`       | **411 µs**  | 2.6×        | `blur 14` 阴影 + 文字          |
| 6  | `text_wrap`   | **390 µs**  | 2.5×        | 折行计算 + 多次文字绘制              |
| 7  | `alert`       | **288 µs**  | 1.8×        | 图标 + 标题 + 折行正文             |
| 8  | `textarea`    | **283 µs**  | 1.8×        | 多行文字 + 边框 + 内边距            |

**谁最便宜**：`separator` 7.5µs、`progress` 9.8µs、`skeleton` 12.9µs、`toggle` 16.6µs。

**三条最重要的结论**：

1. **没有任何组件会在静置时吃 CPU**：47 项全部 **0.00%、0 帧**。  
   `spinner` 和 `skeleton(.animate())` 曾经是真的常驻动画（2.60% / 1.56%），
   当前默认不常驻；spinner 可用 `.animate()` 显式持续播放，skeleton 仍只在悬停时推进。
2. **一帧有 290µs 的地板价**，来自 BitBlt 上屏（690×450 物理像素）。  
   连 `empty`（什么都不画）也要 300µs 一帧，其中 290µs 是上屏。
3. **成本可以按「面积 + 字符数」预估**：  
   `耗时 ≈ 几何面积 × 1.6ns + 字符数 × 10µs + 5µs`，能解释 90% 的实测值。

## 2. 测试方法

### 2.1 为什么每个组件单独一个进程

同一窗口里只要能有一个「自请求重绘」的组件（闪烁的输入框光标、悬停中的 spinner），  
量到的 CPU 就是所有组件混在一起的，无法归因。

所以台架 `tools/probe/perf_comp.cpp` 的做法是：**一个进程只画一个组件**，  
由 `--comp=<name>` 选，驱动脚本 `tools/perf_bench.py` 逐个拉起。

### 2.2 三种工况

| 工况       | 启动参数                     | 采样   | 测什么                        |
| -------- | ------------------------ | ---- | -------------------------- |
| **静置**   | 无 `--anim`               | 3.0s | 有没有偷偷每帧重绘（CPU 应为 0、帧数应为 0） |
| **连续重绘** | `--anim`（每帧 `repaint()`） | 4.0s | 单帧绘制成本（组件调用本身的 QPC 耗时）     |
| **交互**   | 无 `--anim` + 脚本投递鼠标消息    | 6.0s | 真实输入负载下的 CPU 与帧率           |

统一预热 **2.0s** 后开始统计 —— 首帧要建字体缓存、分配后备缓冲，  
混进统计会把「启动成本」错记成「组件成本」。

### 2.3 为什么不用 psutil 的 CPU 时间做主指标

实测发现 Windows 上进程 CPU 记账**按 15.625ms 时钟节拍更新**：  
1.2 秒窗口里读到的 `cpu_sec` 只有 `0.0000 / 0.0156 / 0.0312 / 0.0469 / 0.0625` 这几个离散值。  
在 1~2 秒的窗口里误差能到 ±1.3%，短窗口甚至会读到 0。

所以主指标改成 **QPC（`QueryPerformanceCounter`）直接测组件调用耗时**，  
精度到微秒。CPU 百分比只作为「是否失控」的辅助判据。

### 2.4 分段计时的来源

连续重绘工况下开 `AINO_FRAME_LOG=1`，库每 120 帧打印一次四段耗时：

```
[aino] 120 帧  渲染均 0.89 ms  最差 5.78 ms  (预算 16 ms)
        取输入 0.01 | 绘制 0.68 | 收尾 0.00 | 上屏 0.20  (ms)
```

- **取输入**：消息泵 + 输入状态换算
- **绘制**：`begin_frame` + 用户帧回调（即组件绘制）+ `end_frame`（浮层）
- **收尾**：帧末延迟绘制
- **上屏**：`BitBlt` 到窗口 DC

下表的「帧均」= 渲染均，「上屏」= 该分段。「组件绘制」是台架自己测的、  
只包住组件那一次调用 —— 所以它比「帧均」小（帧均还含框架与上屏）。

## 4. 成本模型（从实测反推）

### 4.1 一条文字 ≈ 10µs/字符

| 用例                              | 字符数 | 实测       | 折算          |
| ------------------------------- | --- | -------- | ----------- |
| `prim_text`（纯 `draw_text`，17 字） | 17  | 170.1 µs | 10.0 µs/字   |
| `label`（17 字）                   | 17  | 156.5 µs | 9.2 µs/字    |
| `button`（"保存" 2 字）              | 2   | 137.3 µs | 其中文字 ≈ 20µs |

所以 `draw_text` 的单价是**每字符约 10µs**（14px 中文，含字形缓存命中）。

这解释了为什么「文本框」和「面板」看起来都是"一块底"，成本却差好几倍：  
真正贵的是字，不是底。

### 4.2 几何填充 ≈ 1.6 ns/像素 + 约 6µs 固定

| 用例                          | 面积（逻辑 px²） | 实测      | 折算        |
| --------------------------- | ---------- | ------- | --------- |
| `prim_rrect`（320×100 圆角 16） | 32000      | 51.1 µs | 1.6 ns/px |
| `progress`（320×8，两次填充）      | 5120       | 9.8 µs  | 1.9 ns/px |
| `separator`（320×1）          | 320        | 7.5 µs  | 固定开销为主    |
| `skeleton`（320×16 圆角 8）     | 5120       | 12.9 µs | 2.5 ns/px |

圆角比直角贵（边缘要走覆盖率 AA），但量级仍然是「面积 × 纳秒级」。

### 4.3 阴影 ≈ 6.5 ns/像素 + 51µs 固定开销

阴影不是按"轮廓面积"收费的：`raster_shadow` 遍历的是**外扩 `blur` 之后的
包围盒**（每边各扩 `blur` + 1），并且全部按物理像素算。所以正确的测法是
固定 blur、只改尺寸，看耗时怎么走。

三档阶梯（逻辑尺寸 → 物理包围盒 → 实测）：

| 用例 | 面板（逻辑） | blur | 物理包围盒 | 实测 |
| --- | --- | --- | --- | --- |
| `shadow_s` | 160×40 | 10 | 270×90 = 24300 px² | 208.8 µs |
| `shadow_m` | 260×80 | 22 | 456×186 = 84816 px² | 634.9 µs |
| `shadow_l` | 340×170 | 22 | 576×321 = 184896 px² | 1252.9 µs |

线性拟合（取首尾两点）：

```
耗时 ≈ 面积 × 6.50 ns + 50.8 µs
```

用中间一点校验：`84816 × 6.50ns + 50.8µs = 602 µs`，实测 **634.9 µs**，偏差 5.4%。

> ⚠️ **这里曾经算错过一次**：最初拿 260×80 的"轮廓面积"（20800 px²）去除
> 615.7 µs，得 29.6 ns/px，还由此推出"阴影占 dialog 的 60%"。
> 错在把包围盒当成了面板本身 —— 误差全部来自被漏掉的 `blur` 外扩区。
> 现在这组阶梯就是为了让"面积"和"外扩"两个变量分开测。

**这条解释了 `dialog` 为什么最贵**：

```
dialog 面板 = 340×170，blur 22，dy 8 —— 与 shadow_l 参数完全相同
       = 阴影 1252.9 µs（实测，占 45.2%）
       + 全屏遮罩 + 面板填充 + 标题 + 正文 ≈ 1520 µs
       ≈ 2773 µs
```

阴影差不多吃掉一半。把 `blur` 从 22 降到 14：包围盒从 576×321 缩到 552×297
（−12%），加上 `blur` 变小后逐像素提前退出的命中率更高，实际能省 15~25%。

### 4.4 模型校验

```
耗时 ≈ 面积 × 1.6ns + 字符数 × 10µs + 5µs
```

| 组件                                | 预测     | 实测     | 偏差   |
| --------------------------------- | ------ | ------ | ---- |
| `label`（17 字）                     | 175 µs | 156 µs | −11% |
| `table`（12 处文字 ≈ 40 字 + 40000px²） | 465 µs | 603 µs | +30% |
| `tabs`（6 字 + 3 次填充 + 3 次文字）       | 130 µs | 218 µs | +68% |
| `panel`（46800 px² + 描边）           | 80 µs  | 119 µs | +49% |

预测偏低的部分都出现在「多次小绘制」的组件上 —— 因为每次 `fill_rect` /  
`draw_text` 调用都有独立的**固定开销**（状态检查、坐标换算、裁剪计算）。  
所以更准确的说法是：

> **成本 ≈ Σ(每次绘制的固定开销) + 字符数 × 10µs + 面积 × 1.6~30ns**

调用次数比面积更重要。这也是 `table`（12 次文字 + 十几条线）比  
`sparkline`（12 条长线）便宜一点、却比同面积的面板贵 5 倍的原因。

### 4.5 圆弧：84 次扫描 → 1 次

`spinner` 原来是 48 段 `raster_line` 拼底环 + 36 段拼弧 = **84 次独立扫描**，
每次都要算包围盒、跑一遍 `blend` 循环。改用 `raster_arc` 之后是**一次**
包围盒遍历：径向距离求覆盖率、极角求 alpha。

实测 **99.1 → 65.8 µs（−34%）**。但性能只是副产品，真正的收益是**画对**：

| 画法 | `alpha=128` 整圈沿角度采样 360 点的亮度 |
| --- | --- |
| 拼 48 段 | 31 ~ 61（落差 **30**）|
| 一次成形 | 127 ~ 127（落差 **0**）|

`raster_line` 两端是圆头，相邻段在接缝处重叠 → 同一像素被 `blend` 两次 → 叠深。
段越密接缝越多，看起来就是一节一节的"拼接块"。

> 教训：**用"拼一堆小图元"近似连续几何，几乎一定付两笔钱** ——
> 重复混合造成的接缝（视觉），和 N 倍的调用次数（性能）。能一次扫描完的就别拼。

| --- | --- | --- |
| `spinner` | 无条件 `repaint()` → **2.60% / 121 帧** | 只在**鼠标悬停**时转 → 0.00% / 0 帧 |
| `skeleton` + `.animate()` | 无条件 `repaint()` → **1.56% / 132 帧** | 只在**鼠标悬停**时呼吸 → 0.00% / 0 帧 |

两者都用**组件自己的局部相位**推进，所以移开再移回来是"接着动"，而不是
跳到全局时钟对应的相位。

spinner 可使用 `Style().animate()` 持续播放；此选项不让 skeleton 常驻。实测（460×300 / 单个 spinner）：
`.animate()` 时约 39fps、0.52%~2.60% CPU（区间取决于窗口是否被遮挡 —— 被挡住时
上屏的 `BitBlt` 不做实际光栅化）。

> 结论：**加新组件时，"静置 0 帧"是硬门槛。** 需要动画就显式 opt-in，
> 而且默认只在悬停时动 —— 常驻动画的代价和窗口面积成正比，不能默认付。

## 6. 交互工况的结论

### 6.1 `tooltip` 测不到显示态（诚实说明）

`tooltip` 的 8.7µs 是「鼠标不在 anchor 内」时的成本 —— 只做了一次矩形命中测试，  
没有任何绘制。这不是 bug，但也**不代表它显示时的开销**。

**为什么测不到**：脚本用 `PostMessage(WM_MOUSEMOVE)` 伪造悬停（不动真实光标）。  
而库在收到 `WM_MOUSEMOVE` 后会调 `TrackMouseEvent(TME_LEAVE)` 注册离开通知；  
系统随即检查**真实**光标位置，发现不在窗口内，立刻回投 `WM_MOUSELEAVE`，  
库把鼠标坐标设成 `-1e6` —— 于是 `tooltip` 的 `anchor.contains(mouse)` 永远为假。

**它的真实成本**应当与 `toast` 同量级（`blur 10` 的阴影比 toast 的 `blur 14` 还轻，  
再加减一行 13px 文字），**约 300~400µs**。这个数字是推算，不是实测，故单独标注。

### 6.2 指针移动：不按时间节流，按「悬停目标有没有变」

0.3.3 之前的结论是「输入帧不节流，投递多快就渲染多快」。现场实测能跑到 90fps，
但那不是优点：Windows 每移动一个像素就发一条 `WM_MOUSEMOVE`，120Hz/1000Hz 鼠标
意味着每秒几百到上千次**整窗重绘**。在 1180×760（1.5× DPI ≈ 2M 像素）上实测：

| 工况 | 单核（本机 16 核） | 说明 |
|---|---|---|
| 0.3.2：指针画圈 3 秒，来一条画一条 | **99.9%** | 每条 `WM_MOUSEMOVE` 都整窗重绘 |
| 0.3.3 初版：所有移动帧按 33ms（30fps）合并 | **17~23%** | 省了 CPU，但高亮跳格、会画出空帧 |
| 0.4.x：悬停目标没变就不画（扫导航 / 同一行内抖） | **18% / 1.6% = 12×** | 只有跨控件边界才画一帧 |

30fps 那一版虽然省 CPU，但代价是看得见的：指针扫过一排条目时，高亮按 30fps
跳格，中间还会画出「谁都没 hover」的空帧，看着就是闪一下。根因不是帧率不够，
是**画了不该画的帧** —— 指针在同一个按钮内部移动时，画面一个像素都不会变。

所以判据从「多久画一次」换成「需不需要画」：

- 指针移动时先看**上一帧的悬停矩形**。还在同一个控件内 → 不排帧（0 帧）。
- 不在里面 → 看上一帧的**全部可交互矩形**：落在空白处 → 也不排帧。
- 真的会变（离开旧控件 / 进入某个控件）→ 正常排帧，按 `anim_budget_ms`（60fps）。

于是：在按钮上抖鼠标是 0 帧，扫过一排条目是满刷新率，只有「跨过控件边界」才画一帧。
`move_budget_ms` 仍然保留，但默认等于动画预算；想极省电可以 `set_move_fps(30)`。

副作用只有一个：如果帧回调里画了**跟着指针跑又不经过任何控件**的东西（自定义准星、
拖影、画板笔迹），这套判定会让它停在原地 —— 那种应用调 `set_hover_skip(false)`。

### 6.2.1 这条线怎么断言（为什么不用绝对百分比）

「单核 ≤ N%」这种绝对值**测不出机制**。同一份二进制、同一条轨迹，机器上有 DWM
合成、GDI 字体缓存、其它进程的干扰，实测能在 13%~51% 之间乱跳；拆成 user / system
能看到抖动几乎全在 system 那半边。把阈值调宽到能容纳噪声，就等于什么都没断言。

改成**两条轨迹求比值**，让共同干扰自己约掉：

| 记号 | 轨迹 | 应该 |
|---|---|---|
| **A** | 在左侧导航里上下扫，每 ~30px 换一行（悬停目标一直在变） | 该画，接近满刷新率 |
| **B** | 在**同一行内部**抖 ±4px（悬停目标始终不变） | 理想是 0 帧，实测只剩噪声底 |

判据：`A / max(B, 0.35) ≥ 4`，且 `A ≤ 60%`（后者只防"两条都卡死"的假绿）。

`B` 有下限 0.35% 是因为读数本身有分辨率：B 真的接近 0 时，比值会变成除零游戏。
实测正常状态 `18.2% / 1.6% = 12×`（机器闲）到 `37.0% / 0.5% = 71×`（刚编译完、
A 那半边被负载抬高，比值反而更大）；把 `set_hover_skip(false)` 打开（即打断过滤、
退回"来一条画一条"）后是 `33.3% / 30.2% = 1×` —— 断言确实钉住了机制，不是钉住了机器闲不闲。


### 6.3 交互 CPU 与绘制成本基本正相关

下表是在**旧的全速重绘**下测的（每 10ms 投递一次 `WM_MOUSEMOVE`，约 90fps）。
现在指针移动只在真的改变画面时才画，绝对值降到十分之一以下；但**相对关系不变**，
表仍然可以用来判断"谁贵"。

| 组件          | 组件绘制    | 交互 CPU     |
| ----------- | ------- | ---------- |
| `dialog`    | 2773 µs | **16.12%** |
| `table`     | 603 µs  | **9.37%**  |
| `text_wrap` | 390 µs  | 6.76%      |
| `input`     | 169 µs  | 6.51%      |
| `toast`     | 411 µs  | 5.73%      |
| `separator` | 7.5 µs  | 2.60%      |
| `empty`     | 0.2 µs  | 1.04%      |

`empty` 的 1.04% 是**地板价**（每帧 290µs 的上屏 + 消息处理），  
所以看交互 CPU 时要先减掉这 1% 左右。

`input` 的 6.51% 略高于同等绘制成本的 `nav_item`（5.20%），  
因为它多了文本测量与光标定位。

## 6.5 帧间隔的隐形上限：`Sleep` 只有 15.6ms 精度

前面几节量的是"一帧花多久"，但用户感受到的是**帧与帧之间隔多久**。
这两件事之间还夹着一个主循环的节流：

```cpp
const uint64_t budget_us = uint64_t(budget_ms) * 1000u;   // 16ms
if (el_us < budget_us) Sleep(DWORD((budget_us - el_us + 999) / 1000));
```

Windows 的默认时钟粒度是 15.6ms，`Sleep` 会被向上取整到整数个 tick：

| 调用 | 实际睡了 |
|---|---|
| `Sleep(1)` | 15.6 ms |
| `Sleep(5)` | 15.6 ms |
| `Sleep(15)` | 16.0 ms |
| `Sleep(16)` | 30.9 ms |

后果：绘制 12.5ms + `Sleep(4)` → 28ms/帧。**渲染还有 4ms 余量，画面却被钉在 33fps。**
而且帧间隔整齐地停在 28~32ms（不是抖动的长尾），这正好是"被量化"的指纹 ——
如果看到这种形状，先怀疑定时器，别去优化绘制。

修法用 `CreateWaitableTimerExW` + `CREATE_WAITABLE_TIMER_HIGH_RESOLUTION`
（Win10 1803+，精度约 1ms），**只影响本进程等的那一下**：

```cpp
HANDLE h = CreateWaitableTimerExW(nullptr, nullptr, 0x2, TIMER_ALL_ACCESS);
LARGE_INTEGER due; due.QuadPart = -LONGLONG(us * 10);   // 相对时间，100ns
SetWaitableTimer(h, &due, 0, nullptr, nullptr, FALSE);
WaitForSingleObject(h, INFINITE);
```

不用 `timeBeginPeriod(1)`：那是全局把系统时钟中断调快，空闲时也会压着 CPU 不降频，
和"空闲 0% CPU"的承诺冲突。

实测（gallery，1180×760，Button 页）：**30.25 ms → 16.27 ms（33.1 → 61.5 fps）**，
最差帧 37.6 → 18.3 ms，没有一帧超过 20ms。

量它需要一个"连排 N 帧并记录每帧开始时刻"的钩子（光有渲染耗时看不到空档）：

```bash
AINO_BENCH_RUN=90 AINO_FRAME_LOG=o.txt build/Release/aino_gallery.exe
```

## 7. 优化建议

### 7.1 按「贵」的顺序避开

| 场景   | 建议                                                           |
| ---- | ------------------------------------------------------------ |
| 模态框  | `dialog` 单帧 2.8ms。别在对话框打开时做定时刷新，一帧超过 16ms 预算的 17%            |
| 实时图表 | `sparkline` 867µs。**不要每帧重画**，数据变了才画；点数从 12 降到 6 能省近一半（线段数减半） |
| 阴影   | `blur` 每加一倍，有效核面积翻 4 倍。`dialog` 用 22 是"要压住整页"的代价，非必要别学       |
| 表格   | `table` 603µs 主要花在 12 次 `draw_text` 上。行数翻倍成本近似翻倍             |
| 长文本  | `text_wrap` 390µs = 折行计算 + 3 次文字绘制。静态段落建议缓存高度，不要每帧重算         |

### 7.2 三条通用规则

1. **减少绘制调用次数**，而不是减少绘制面积。  
   十个小矩形比一个大矩形贵。
2. **文字是主要成本**（10µs/字符）。  
   一屏 100 个汉字 = 1ms，这已经是 60fps 预算的 6%。
3. **能静态就别动画**。  
   一个常驻 `spinner` 让整页从 0 帧变成 40fps，代价是 2.6% 的 CPU。
   默认的"悬停才动"就是为这条设的 —— 用户不碰它的时候，它是 0 帧。

### 7.3 窗口尺寸的影响

上屏成本（290µs）与窗口面积成正比：690×450 物理像素 → 290µs。  
把窗口从 460×300 缩到 320×200，上屏约降到 150µs，**地板价直接砍半**。

这就是为什么"小工具窗口"的帧率总是比"全屏应用"好看 ——  
不是组件画得快，是 BitBlt 搬的像素少。

## 8. 测试的局限（必须知道的四点）

1. **窗口必须可见**。被别的窗口挡住时，窗口 DC 的可视区为空、`BitBlt` 不做  
   实际光栅化，同一页能读到 0%~45%。台架全程用 `SetWindowPos(HWND_TOPMOST)`  
   保证可见，但这意味着**数据是在"最坏可见情况"下测的**。
2. **模拟鼠标不等于真实鼠标**。`PostMessage` 伪造的悬停会被系统的  
   `MOUSELEAVE` 抵消（见 6.1），所以本测试的"交互"衡量的是  
   **高频输入下的渲染吞吐**，不是 hover 高亮的开销。
3. **CPU 百分比有 15.6ms 的量化误差**。6 秒窗口下约 ±0.26%，  
   个位数差异（比如 0.78% vs 1.30%）不应当作显著区别。
4. **单组件隔离**。真实页面里多个组件共享一次清屏与上屏，  
   所以「把 10 个 label 的成本相加」会高估整页成本 ——  
   上屏那 290µs 只付一次。

## 10. 大文本 / 滚动 / 动画的开销（0.2 实测）

这三块不是"单组件"，所以不进军架表，单独测：

| 项目 | 数字 | 说明 |
|---|---|---|
| 折行 20 万字（首次） | **1.66 ms** | 逐字量宽 + 分配行字符串 |
| 折行 20 万字（缓存命中） | **6.5 µs** | 一次哈希 + 一次 `memcmp`，约 **250 倍** |
| 单字宽度缓存命中 | ~40 ns | `unordered_map<uint64_t,float>` 一次查找 |
| 滚动（虚拟）1000000 项 | 每帧绘制 **10 项** | 与总项数无关，O(1) 定位 |
| `tween` 运行中 | 一次 map 查找 + 两次插值 | 到点即停，**静止后 0 帧** |
| 变换（无旋转） | 每图元 2 次乘加 | 走原来的专用光栅器，像素与不加变换一致 |
| 变换（有旋转） | 多边形路径 | 圆角矩形每角 5 段，`raster_poly` 扫描线 |

来源：`tools/probe/bigfeat_probe.cpp`（45 项断言）。

> 折行的「首次」包含了单字宽度缓存的填充；同一段文本第二次进入缓存后，
> **整段折行不再发生**，代价只剩哈希 + `memcmp`。这也是"大块文本不卡"的全部秘密 ——
> 没有增量重排，就是干脆不重排。

结果写入 `tools/perf_result.json`，原始 stderr 日志在 `tools/_perf_logs/`。

> 台架只统计「预热之后、`--dur` 之内」的帧。跑满窗口后它**停止统计但不退出**，
> 进程生命周期交给脚本 —— 早期版本到点自动 `win.close()`，和脚本的 CPU
> 采样窗口差 0.1 秒，进程先死、`psutil` 抛 `NoSuchProcess`，整条记录作废。
